# OAuth 2.0

## 1. Introduction to OAuth

OAuth was designed to allow **third-party applications to access protected resources on behalf of a user**.

It was a major improvement over traditional authentication methods such as username and password because it provided a more secure and flexible way to grant access.

However, OAuth 1.0 was relatively complex and difficult to implement and was not as widely supported as traditional authentication methods.

In 2012, **OAuth 2.0** was released to address many of the shortcomings of OAuth 1.0 while also providing new features and improvements.

Today, OAuth 2.0 is widely used by websites and applications such as Facebook, Twitter, and Amazon. It provides a secure way for applications to access a user's data **without requiring the user to share their password with the application**.

In simple terms:

> **OAuth 2.0 is an authorization framework for sharing user authorization across systems.** 

---

# 2. OAuth 2.0 in Simple Terms

OAuth 2.0 allows two applications or systems to communicate without one application needing the user's password.

### Example: Game + Google

Suppose you want to play a game on your computer, but the game requires access to your Google account.

You don't want to give the game your Google username and password.

Instead, OAuth 2.0 can be used.

The flow is:

```text
User
 ↓
Game Website
 ↓
Google Login
 ↓
User authenticates with Google
 ↓
Google grants permission
 ↓
Access Token
 ↓
Game uses Access Token
 ↓
Google APIs
```

The game never needs to know the user's Google password.

Instead, Google provides the game with an **access token**.

The access token acts like a key that allows the game to communicate with Google **on behalf of the user**. 

---

# 3. Access Token

An **access token** is a short-lived credential that allows an application to access a user's protected resources on the user's behalf.

It is important to understand that:

* An access token is **not the user's password**.
* It does not necessarily give the application full access to the user's account.
* It represents specific permissions granted to the application.
* It is typically generated by the **authorization server** after the user grants permission.

The authorization server returns the access token to the application.

The application can then use the access token to make requests to the **resource server**. 

---

# 4. How an Access Token Is Sent

The access token is typically sent using the HTTP `Authorization` header.

For example:

```http
Authorization: Bearer <access-token>
```

The header contains:

* The authentication/authorization scheme, such as `Bearer`
* The access token

The resource server receives the request and validates the access token.

If the token is valid, the resource server allows the application to access the requested resources. 

---

# 5. OAuth 2.0 Authorization Code Flow

The **Authorization Code Flow** is one of the main OAuth flows discussed in the lecture and is used when an application needs to access protected resources **on behalf of the user**.

### Example: Login with Google

Suppose an application provides:

```text
Login with Google
```

The flow is:

```text
User
 ↓
Application
 ↓
Google Authorization Server
 ↓
User logs in
 ↓
User grants permission
 ↓
Authorization Code
 ↓
Application
 ↓
Authorization Server
 ↓
Access Token + Refresh Token
 ↓
Application
 ↓
Google APIs
```

### Step-by-step

1. The user visits the application.
2. The user clicks **Login with Google**.
3. The application redirects the user to Google's authorization server.
4. Google asks the user to log in.
5. The user enters their credentials.
6. The user grants permission.
7. Google redirects the user back to the application with an **authorization code**.
8. The application sends the authorization code to the authorization server.
9. The authorization server validates the code.
10. The authorization server returns an **access token** and potentially a **refresh token**.
11. The application uses the access token to access Google's APIs.

The access token is valid only for a certain amount of time. After it expires, the application needs to obtain a new access token. 

---

# 6. Why Access Tokens Are Important

OAuth access tokens allow applications to access protected resources **without requiring the user's password to be shared with the application**.

This provides better:

* Security
* Privacy
* Control over permissions

For example:

```text
Without OAuth:

User Password
     ↓
Third-Party Application
     ↓
Google
```

The application would have the user's password.

With OAuth:

```text
User Password
     ↓
Google
     ↓
Access Token
     ↓
Third-Party Application
     ↓
Google APIs
```

The third-party application receives the access token rather than the user's password. 

---

# 7. Resource Server

The **resource server** is the system that hosts the protected resources that the application wants to access.

In the Google example:

```text
Google APIs
```

are the resource servers.

The resource server's responsibility is to evaluate the access token.

It does not necessarily perform the user's login itself.

The basic process is:

```text
Application
    ↓
Access Token
    ↓
Resource Server
    ↓
Validate Token
    ↓
Valid?
 ↓       ↓
Yes      No
 ↓        ↓
Allow    Reject
```

The resource server can be implemented in different ways depending on the use case. It could be a:

* Web application
* Mobile application
* Cloud service
* API

The important concept is that the resource server hosts the protected resources. 

---

# 8. OAuth 2.0 and JWT

**OAuth 2.0 and JWT are two different things.**

OAuth 2.0 is an **authorization framework**.

JWT is a **token format**.

They can work together.

```text
OAuth 2.0
   ↓
Defines authorization process
   ↓
Access Token
   ↓
JWT can be used as the token format
```

JWTs can represent OAuth access tokens because JWTs are self-contained and can be verified by the resource server.

For example, suppose a third-party application wants access to a user's Google Calendar.

```text
User
 ↓
Third-Party Application
 ↓
OAuth 2.0
 ↓
Google Authorization Server
 ↓
Access Token
 ↓
JWT
 ↓
Google Calendar Resource Server
```

The resource server can verify the JWT and grant the application access to the calendar. 

---

# 9. Benefits of Using JWT with OAuth 2.0

JWTs provide several benefits when used with OAuth 2.0.

### Self-contained

A JWT can contain information about the authorization and identity in the token itself.

The resource server can verify the token without necessarily needing to contact another server for every request.

### Compact

JWTs are compact and URL-safe, making them easy to transmit over a network.

### Claims

JWTs can contain different claims, such as:

* Identity
* Authorization information
* Other relevant data

This makes JWTs flexible for different use cases. 

---

# 10. OAuth 2.0 vs JWT

This is one of the most important concepts to understand.

| OAuth 2.0                       | JWT                                                      |
| ------------------------------- | -------------------------------------------------------- |
| Authorization framework         | Token format                                             |
| Defines how authorization works | Defines how information is represented                   |
| Defines flows                   | Contains claims                                          |
| Can issue access tokens         | Can be used as an access-token format                    |
| Handles delegation of access    | Provides a compact, signed representation of information |

Therefore:

> **OAuth 2.0 does not mean JWT. JWT does not mean OAuth 2.0. They are different technologies that can work together.** 

---

# 11. Identity Provider

An **Identity Provider (IdP)** is responsible for authenticating the user.

For example:

```text
Google
```

can act as an Identity Provider.

The user authenticates with Google, and Google establishes the user's identity.

In the Google example, Google can act as both:

* Identity Provider
* Authorization Server

because Google can authenticate the user and issue the access token. 

---

# 12. Authorization Server

The **Authorization Server** is responsible for issuing access tokens after the appropriate authorization process.

Its responsibilities include:

* Processing authorization requests
* Obtaining/confirming user consent
* Issuing access tokens
* Potentially issuing refresh tokens

The lecture emphasizes an important distinction:

> The **Identity Provider authenticates the user**, while the **Authorization Server issues access tokens**.

Sometimes these roles are performed by the same entity, and sometimes they are separate. 

---

# 13. Identity Provider vs Authorization Server

```text
                 User
                   │
                   ▼
          Identity Provider
                   │
            Authenticate
                   │
                   ▼
          Authorization Server
                   │
             Issue Token
                   │
                   ▼
             Access Token
                   │
                   ▼
           Resource Server
```

However, these do not have to be separate systems.

For example, Google can provide both authentication and authorization services.

Another company might use:

```text
Third-Party Identity Provider
          ↓
     Authenticate User

Company Authorization Server
          ↓
     Issue Access Token

Company Resource Server
          ↓
     Protected Resources
```

This separation is important in larger enterprise architectures.

# 14. OAuth 2.0 Flows

The lecture discusses four OAuth 2.0 flows:

1. Authorization Code Flow
2. Client Credentials Flow
3. Resource Owner Password Flow
4. Implicit Flow

The appropriate flow depends on the application's requirements. 

---

## 14.1 Authorization Code Flow

The Authorization Code Flow is used when an application needs to access protected resources **on behalf of a user**.

```text
User
 ↓
Application
 ↓
Identity Provider
 ↓
User Authentication
 ↓
Authorization Code
 ↓
Application
 ↓
Authorization Server
 ↓
Access Token + Refresh Token
 ↓
Resource Server
```

The application does not directly receive the user's password.

Instead, it receives an authorization code and exchanges that code for tokens. 

---

## 14.2 Client Credentials Flow

The **Client Credentials Flow** is used when the application needs to access protected resources **on its own behalf**, rather than on behalf of a user.

For example, one backend service needs to communicate with another backend service.

The application authenticates using:

```text
Client ID
+
Client Secret
```

The authorization server then returns an access token.

```text
Application
    ↓
Client ID + Client Secret
    ↓
Authorization Server
    ↓
Access Token
    ↓
Resource Server
```

There is no user login involved in this flow because the application itself is the entity requesting access. 

---

## 14.3 Resource Owner Password Flow

The **Resource Owner Password Flow** is used when an application needs access to a user's protected resources but the user does not want to be redirected to the Identity Provider.

Instead, the application asks the user directly for their:

```text
Username
Password
```

The application then sends those credentials to the authorization server.

The authorization server validates them and returns:

```text
Access Token
+
Refresh Token
```

The application can then use the access token to access the resource server. 

> **Note:** The transcript describes this flow as one of the OAuth 2.0 flows, but it is important to recognize that this is an older flow and is not recommended for modern applications.

---

## 14.4 Implicit Flow

The **Implicit Flow** is described as a simplified version of the Authorization Code Flow.

In this flow:

```text
User
 ↓
Application
 ↓
Authorization Server
 ↓
Access Token
 ↓
Redirect back to Application
```

The authorization server redirects the user back to the application with an access token in the URL.

The application can then use the access token to access the resource server.

However, the implicit flow is less secure than the Authorization Code Flow and is not recommended for most modern applications. 

---

# 15. Comparison of OAuth 2.0 Flows

| Flow                        | Used For                                       | User Involved? |
| --------------------------- | ---------------------------------------------- | -------------- |
| **Authorization Code**      | Access resources on behalf of user             | Yes            |
| **Client Credentials**      | Application/service accessing resources itself | No             |
| **Resource Owner Password** | Application directly receives user credentials | Yes            |
| **Implicit**                | Simplified authorization flow                  | Yes            |

The lecture emphasizes that the best flow depends on the specific application and its requirements. 

---

# 16. Complete OAuth 2.0 Architecture

The major components can be understood together as follows:

```text
                         USER
                           │
                           ▼
                    APPLICATION
                           │
                           │ Authorization Request
                           ▼
                 AUTHORIZATION SERVER
                    /              \
                   /                \
                  ▼                  ▼
        IDENTITY PROVIDER        ACCESS TOKEN
          Authenticate                │
                                      ▼
                              RESOURCE SERVER
                                      │
                                      ▼
                              Protected Resources
```

A more complete flow is:

```text
1. User wants to access a protected resource
                    ↓
2. Application requests authorization
                    ↓
3. User authenticates with Identity Provider
                    ↓
4. User grants permission
                    ↓
5. Authorization Server issues authorization code
                    ↓
6. Application exchanges code for access token
                    ↓
7. Application sends access token to Resource Server
                    ↓
8. Resource Server validates token
                    ↓
9. Resource Server provides protected resource
```

# 17. OAuth 2.0 and Single Sign-On

OAuth 2.0 can be part of systems that provide **Single Sign-On (SSO)**.

For example:

```text
User
 ↓
Google Login
 ↓
Authenticate Once
 ↓
Application receives authorization
 ↓
Access Google Resources
```

The user does not need to provide their Google password to the third-party application.

The application instead works with the authorization granted through the OAuth process. 

---

# 18. Important Concepts to Remember

### OAuth 2.0

OAuth 2.0 is an **authorization framework** that allows applications to access protected resources without sharing the user's password.

### Access Token

A short-lived credential used by an application to access protected resources.

### Authorization Server

Responsible for issuing access tokens.

### Identity Provider

Responsible for authenticating users.

### Resource Server

Hosts the protected resources and validates access tokens.

### JWT

A token format that can be used to represent an OAuth access token.

### OAuth Flow

Defines how the application obtains authorization and tokens.
